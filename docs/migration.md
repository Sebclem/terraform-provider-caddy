# Rebuild migration

The provider now covers the active inventory patterns. Migration rebuilds configuration during an operator-controlled maintenance window; downtime is acceptable. Existing ID-less Caddyfile objects are not imported or patched with IDs. This runbook does not authorize a production cutover.

1. Build/install the provider for your chosen CLI and review the typed [home example](../examples/home/README.md). Supply real bcrypt hashes through a protected variable workflow. Verify certificate/key paths, error files, log-directory permissions, static backend addresses and trusted proxy ranges on the Caddy host. Named routes/relay are intentionally outside active migration.
2. Export `GET /config/` from the admin endpoint to a protected backup. Also keep the current Caddyfile, service startup configuration and deployed provider/state versions. Treat backups/state as secrets. Record which service user owns Caddy's autosaved configuration.
3. Stop Ansible configuration writes and reloads for this instance (`caddy_config_update` and any scheduled/manual reload paths). Installation and file provisioning may remain with Ansible, but must not overwrite or reload the managed configuration. Keep one state owner and one CLI for the instance.
4. Arrange an externally managed HTTP/HTTPS admin endpoint and API-compatible startup persistence. Caddy must start from/resume its API-managed saved configuration under the same service identity/data directory. Verify `caddy run --resume` or the equivalent service setup before handing over ownership. The provider does not change the admin listener or service. See [Caddy API persistence](https://caddyserver.com/docs/api).
5. In the maintenance window, remove the old HTTP/TLS app configuration and legacy logging under operator control. Retain an object root and the working admin endpoint; use an externally loaded admin-only bootstrap configuration. Preserve any required external HTTP/HTTPS app port settings. This intentionally stops serving old routes. Root replacement or `/load` is an operator action, never provider CRUD.
6. Run `tofu init`, `tofu validate`, review `tofu plan`, then `tofu apply` against the bootstrap. Terraform supports the same workflow as the alternative state owner. Certificate files load before HTTPS servers. Routes are active while incomplete; partial routing during apply is expected. Earlier successful resources remain if a later operation fails. Resolve the reported configuration issue and apply again; do not reload the old Caddyfile over partially managed state.
7. Verify every hostname: certificate/SNI and HTTP redirects, authentication before access denial, trusted/untrusted client-IP handling, static proxy traffic and configured health probes, Unifi Host override, Speedtest buffering, WebDAV methods, Jellyfin `/metrics`, per-host logs, error pages and metrics. Jellyfin's exact `/metrics` access-check branch continues to the application proxy for allowed clients, matching the legacy adapter.
8. Run a second detailed plan and apply; require no changes and no admin mutations. Restart/resume under operator control and repeat refresh/plan to validate your service persistence setup. Protect and back up the resulting state.

For recovery during the maintenance window, stop provider applies and restore the protected exported configuration using the external admin/service workflow. Confirm the legacy behavior before reopening traffic. Restoring the backup creates a mismatch with partially built provider state: keep it quarantined and plan a fresh controlled rebuild before resuming provider management. Do not apply the old state blindly over the recovered configuration. The provider does not perform whole-instance rollback.

Certificate renewal and same-path file changes require an external reload; Terraform/OpenTofu detect configured path changes, not remote file contents. Caddy can also retain a log writer when its filename stays unchanged; applying rotation/mode changes may require an operator restart. Neither is service-management functionality in this provider.

The automated disposable rehearsal (`TestAccHomeRebuild`) renders the actual legacy behavior with synthetic local services, exports it, externally bootstraps an empty instance, applies the typed 49-site example, compares requests and logs, checks a no-change second apply, destroys managed resources and restores the export to verify recovery. It never uses production credentials, backends, installation, DNS or monitoring tasks. See [test matrix](testing.md) for executed versions and evidence.
